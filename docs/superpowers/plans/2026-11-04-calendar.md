# Calendar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A facility sees what every open maternal episode owes on one day, and one woman sees her whole arc on one screen.

**Architecture:** `calendar` becomes a fifth view kind. A new pure module, `kernel/cohort.py`, answers "what does this workflow owe between two dates" by deriving contacts across every open episode of the declared types; nothing is stored. `kernel/views.py` grows a `calendar` branch returning the day's contacts as `rows` and the surrounding month's per-day counts as `groups`, so the existing `GET /views/{id}` route and the existing `ViewResult` shape carry it unchanged. The patient year view is the existing `Arc` at a second scale and needs no new route.

**Tech Stack:** Python 3.9 + FastAPI + stdlib sqlite3 (kernel, api), Go 1.25 (`care_phc_mcp`), React 19 + TypeScript 5.9 + Vite 7 with hand-written CSS (`web`).

**Spec:** `docs/superpowers/specs/2026-11-04-calendar-design.md`

## Global Constraints

- **Nothing is stored.** No task may write a contact, a due date or a count to any table, cache or file. A contact exists only as the return value of a derivation.
- **The renderer may never name a station, flag, capability, operation or view column.** Everything a screen shows comes from the declaration or the kernel's answer.
- **Two engines.** Every kernel route is served by Python and by Go; `scripts/check_go_parity.py` diffs two live kernels and must pass.
- **The gate.** `sh scripts/check.sh` must exit 0 with "all checks passed" before any task is complete.
- **The Store protocol stays at its existing method set.** `select(resource, *, thread, where, fields, limit)` with `thread=None` reads across threads and is the only read this feature needs. Adding a Store method is out of scope for this plan and returns to the owner as its own decision (spec §6).
- **The day screen is maternal only:** episode types `pregnancy` and `postnatal`. Referrals are not on it (spec §2.8).
- **A row names the role, never a worker** (spec §2.7).
- **Contact states are exactly** `upcoming`, `due`, `done`, `missed`, from `kernel/schedule.py`.
- Commit messages end with `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
- The working copy is shared with another session. Stage only the files each task names.

## Review Focus

Five conditions the spec implies that no task's own happy path exercises. Each has its test added to the task that owns the code.

1. **An open pregnancy nobody has dated.** `schedule.contacts()` returns `[]` for it. She must appear on no day and must not be counted, and the sweep must not raise. Test in Task 2.
2. **Two pregnancies for one woman inside one window.** The year view must draw them as two arcs, not merge them into one. Test in Task 7.
3. **A day in the past whose episode has since ended.** `contacts()` returns `[]` for an ended episode, so the day reads empty. It must render as "nothing owed" and must not raise or draw a half row. Test in Task 3.
4. **A centre with no open episodes at all.** The day screen and the month counts must both render, empty, rather than blank or erroring. Test in Task 5.
5. **A day asked for outside the month whose counts are returned.** The route takes one date; the counts cover that date's own month. Asking for 31 October must not return November's counts. Test in Task 3.

### Task 2: The sweep — what a centre owes between two dates

**Files:**
- Create: `kernel/cohort.py`
- Test: `kernel/tests/test_cohort.py`

**Interfaces:**
- Consumes: `schedule.contacts(bundle, store, workflow, episode, *, at=None)`; `store.select(resource, *, thread, where, fields, limit)`.
- Produces:
  ```python
  def owed(bundle, store, workflow, *, types, since, until, at=None) -> list
  ```
  `types` is a sequence of episode type names, `since` and `until` are `datetime.date`. Returns a list of dicts sorted by `due` then `subject`, each being a `schedule.contacts()` entry with three keys added: `subject` (the patient id), `subject_row` (the patient's own record, as `dict`), and `on` (the list of ISO dates in the window that this contact covers).

The last two are the point of the feature: the sweep reads episode rows directly, so a woman with no recent encounter is found, and a referral episode is not.

- [ ] **Step 2: Run them to verify they fail**

Run: `python3 -m pytest kernel/tests/test_cohort.py -v`
Expected: FAIL — no module named `kernel.cohort`

- [ ] **Step 3: Implement `kernel/cohort.py`**

Module docstring in the house style: this is `kernel/spine.py`'s episode pairing widened from one subject to all of them, it stores nothing, and it costs one audit read per encounter of each open episode — state that cost and state that the fix if it bites is a bulk read, never a stored contact.

The algorithm the signature does not determine:
1. One `select` per named type over the episode resource with `thread=None`, giving every episode row at the centre.
2. Group by patient, then pair openings with endings using **the same sort as `kernel/spine.py:episodes()`** — `(created_date, 1 if status == "ended" else 0)`, so an opening beats an ending at an equal timestamp.
3. For each still-open episode, select that patient's encounters and attach them as `encounters`, which `schedule.contacts()` needs for its closures.
4. Call `schedule.contacts()` per open episode; drop any contact whose `[opens, closes]` does not intersect `[since, until]`, except a `missed` one, which stays owed after its window shuts.
5. Attach `subject`, `subject_row` and `on`.

Run: `python3 -m pytest kernel/tests/test_cohort.py -v`
Expected: PASS
